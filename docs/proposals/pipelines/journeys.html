From a startup's first deploy to a thousand services

This page sets out where Bemmoly Pipelines stands in the market and the choices a company makes when it adopts it. It then walks through four journeys, from three engineers to five hundred, and says what each one needs from the code on main today.

Where Pipelines stands

Pipelines builds, releases and deploys a company's software on the company's own cloud. A startup uses it like a hosted platform in its first hour. A five-hundred-engineer company runs it as its delivery platform. Nothing in between needs a migration, every part works alone, and every choice can be changed later.

The market splits into four kinds of product, and each one is strong at one end and weak at the other:

The gap. No product covers every step from code to running service on the company's own cloud, is open source and self-hosted, and grows from three engineers to five hundred without changing systems. Harness comes closest on coverage, but it asks for many concepts on day one and is priced for enterprises. The managed-cloud platforms come closest on the first hour, but none of them creates a project per environment, and they stop at small teams. Pipelines can own that space because the kernel already gives it teams, SSO, audit and access for free.

Rules for every decision

  • Their cloud, their bill.Builds, images, logs, caches and services all live in the company's own accounts. Bemmoly never runs their workloads and never charges for them.
  • Start as a platform, grow without migrating.The startup path writes real, readable files. Going off the default path means editing a file, never switching to a different system.
  • Every part works alone.Build, release, deliver, clouds and the catalog each work without the others, joined by stated contracts.
  • No one-way doors.Every choice is a setting. Changing it produces a plan that shows what moves, what it costs and any downtime. Everything Pipelines creates can be exported as Terraform and Helm.
  • Hide it until it is needed.Approvals, policies, canaries, tiers and runner pools appear when something calls for them, such as a second team or a first Prod target.
  • Governance is never a paid extra.SSO, audit, teams and access come from the kernel and are on from the first day, at any size.

Folder, not organization

You suggested giving Pipelines organization-level access. I recommend a narrower grant with the same effect. The setup script runs once with the admin's own sign-in, creates a folder named Bemmoly, and grants Pipelines roles on that folder only. Pipelines can then create any project it needs inside the folder, but it cannot see or change anything outside it. This keeps the "Pipelines does everything" experience and removes the scariest part of the security review.

Pipelines needsRoleGranted on
Create projectsroles/resourcemanager.projectCreatorThe Bemmoly folder
Create sub-folders, for the Enterprise layoutroles/resourcemanager.folderCreatorThe Bemmoly folder
Link new projects to billingroles/billing.userOne billing account
Everything inside a project it createdOwner, which Google gives a project's creator automatically. Pipelines then swaps it for the narrower roles each project needsEach new project

That is the whole managed grant. Two details shape the setup screen. Linking billing is a separate call after a project is created, and a new project's permissions can take minutes to settle, so each step waits and retries. A billing account can also link only a few projects until Google raises the limit. Setup counts the projects a layout needs and checks that headroom before it starts, and it says how to ask for more.

In attached mode the grant is smaller still. For Cloud Run it is roles/run.developer, permission to act as the service's runtime account, and read access to the registry. For an existing GKE cluster it is roles/container.clusterViewer plus Kubernetes rights in named namespaces only. The broader GKE developer role is avoided because it reaches every cluster in the project.

Pipelines signs in to Google Cloud without key files. It uses the service account of the VM it runs on, or workload identity federation with Pipelines' own public keys uploaded to Google, which works even when Bemmoly is not reachable from the internet. The federation pool lives in the company's control project, not in anything Bemmoly owns. That matters because organizations created since May 2024 restrict grants to their own domain by default. Setup reads the organization's policies first, names any that would block it, and says what to ask for, rather than failing halfway.

Projects and clusters

The recommendation is a separate project per environment, and a separate cluster per environment inside its own project. In Google Cloud the project is the boundary for access, billing, quotas and audit. Keeping Dev and Prod apart means a mistake, an upgrade or a quota problem in Dev cannot reach Prod. Google's own enterprise foundation blueprint does the same.

A single cluster holding every environment is the pattern to avoid. Inside an environment's cluster, teams share it through namespaces, one namespace per group in the catalog, with that group's quotas and network rules. Services on Cloud Run need no cluster at all. A cluster exists only when a service in that environment chooses GKE.

LayoutProjectsClusters, when a service needs oneFitsDefault for
StarterThree: platform, non-production and productionOne per project. Dev and Staging share the non-production one as namespacesA small team watching costUnder 20 engineers
StandardOne per environmentOne per environment and regionMost companies20 to 150 engineers
EnterpriseOne per domain and environmentA shared cluster per environment and region. Dedicated clusters for Tier 0 or regulated domainsMany teams with hard walls between themOver 150 engineers

Standard and Enterprise also have two shared projects: a control project where Bemmoly itself runs, and a CI project for build machines, caches and the registry. Starter folds both into one platform project, to stay inside a new billing account's project limit. In every layout, no environment project can push images or change another.

Acme organization └─ Bemmoly folder, the only place Pipelines has rights ├─ acme-control Bemmoly itself ├─ acme-ci runner pool, shared registry, build caches ├─ acme-dev Cloud Run services · GKE Autopilot cluster if needed ├─ acme-staging same shape as Prod └─ acme-prod its own deployer identity, its own audit log

When Pipelines creates a cluster it also runs it. It enrolls the cluster in the Regular release channel and sets maintenance windows. It handles upgrades, Workload Identity and the gateway, and on GKE Standard it also manages node pools. When a cluster is attached, Pipelines only deploys into its namespaces and never touches the cluster itself.

What a cluster costs. Every GKE cluster carries a management fee of $0.10 an hour, about $73 a month. Google's free tier covers one zonal or Autopilot cluster per billing account. So a Starter company that moves one service to GKE pays the fee once, for its second cluster. The switch plan shows that figure before anything is created.

Where each service runs

Each service picks its runtime, so one company can run some services on Cloud Run and others on GKE. A service describes what it needs: its port, health check, CPU, memory, scaling and any long-running work. Pipelines suggests a runtime from that description and explains why. It warns before offering a runtime the service does not fit.

The same runtime all the way to Prod. By default a service uses the same runtime in every environment on its path, so what Staging tested is what Prod runs. Previews may differ, for example a cheap Cloud Run preview for a service that runs on GKE in Prod. Any other difference shows as a warning on the Promote screen.

App Engine is not offered. Google is winding it down and points its users to Cloud Run.

Registry and storage

An image is built once and deployed by its digest everywhere, so Prod runs exactly the bytes that Staging tested.

ChoiceHow it worksFits
One shared registry (default)Artifact Registry in the CI project. Tags cannot be overwritten. Each environment project gets pull-only accessAlmost everyone
A separate Prod registryAt promotion to Prod, the image is copied into a Prod-only registry by digest. It is the same image, so nothing is rebuiltCompanies that want Prod to pull only from inside Prod
Their own registryAny OCI registry: ECR, GitHub's registry, Harbor, JFrog, Docker Hub. Pipelines stores references, never imagesCompanies that already have one

Images that run anywhere are never cleaned up. Images that were never deployed expire after a set time, and scanning runs on push. Storage follows the same rule. Build caches, artifacts, logs and test results go to the company's own Cloud Storage or S3 bucket, with retention set per kind: years for Prod deploy evidence, two weeks for pull-request logs. Local disk is only for a laptop trial.

Who supplies the build machines

The company does. Bemmoly never runs builds on its own machines. A company can mix these per team or per pipeline:

Their existing CIGitHub Actions or another tool keeps building. Pipelines takes over from the built imageYears of build scriptsExists

Builds stay away from Prod. The build identity can push to the registry and nothing else. Each environment deploys with its own identity. A compromised build can publish a bad image, but it cannot touch Prod, and that image still has to pass every gate on the way.

Switch any time

Every choice on this page can be changed later. Changing one produces a plan first, showing what moves, the cost difference, whether there is downtime, and any step a person must do by hand. Three things make that possible:

  • A stable front door per service. Each service gets a domain and a load balancer that Pipelines owns. Google's global load balancer can send weighted traffic to Cloud Run and to GKE at once, so moving between them is a canary: a small share on the new runtime, then more, then all. Going back is shifting the weight back.
  • The same image everywhere. A move never needs a rebuild.
  • A neutral service description. The service's own file does not change when its runtime does.
SwitchHow it goesDowntime
Build machinesThe next run uses the new choiceNone
RegistryImages in use are copied by digest, then deploys pull from the new registryNone
Cloud Run to GKE, or backA traffic shift through the front door. Going to Cloud Run is offered only if the service fits itNone
Layout, such as splitting non-production into Dev and StagingNew projects are created and services redeployed there. Traffic moves, then the old ones are drainedNone for stateless services
Managed to attachedPipelines gives up its folder roles and keeps only each project's deployerNone
Attached to managedPipelines adopts existing projects as they are and recreates nothingNone
Leaving PipelinesEverything it created exports as Terraform and Helm, and keeps running without itNone
Data is the exception. Databases, buckets and queues cannot move by shifting traffic. When a switch involves one, the plan lists it and leaves that step to its owner. Pipelines never moves data on its own.

A startup's first hour

Who Three engineers, one of them a recent graduateHas A Google Cloud account with a card, two GitHub repositories with DockerfilesGoal Both apps in Prod today
  1. Run one command in Cloud Shell, as the account's admin. about 8 minChecks the billing account can link three projects. Creates the Bemmoly folder, the platform project with a small VM running Bemmoly, and the non-production and production projects.
  2. Sign in with Google, then install the GitHub App on the two repositories. 2 min
  3. Pipelines reads both repositories and proposes two applications on Cloud Run, with their ports and health checks found in the code. Accept both. 2 minOpens one pull request per repository adding a short .bemmoly/application.yaml.
  4. Merge the pull requests. The first builds run on Cloud Build, because no cluster exists yet. 5 minPushes each image to the shared registry, then deploys it to Dev with a URL.
  5. Open a pull request with a change. Its preview URL appears on the pull request within minutes, and it is deleted when the pull request closes.
  6. Press Promote to Prod. The first time, Pipelines offers to require one approval for Prod. They can skip it. 5 minRolls out gradually and rolls back on its own if errors rise.

Hidden from them: tiers, policies, runner pools, teams, canary settings and the release map. Each appears when something calls for it.

Done means an empty Google Cloud account reaches a Prod deploy in under 45 minutes, on a real account, recorded end to end.

Growing to 40 engineers

Who The same company a year later, four teamsHas 25 services on Cloud Run, the Starter layoutGoal More safety, faster builds, one service that needs Kubernetes
  1. A second team signs in through SSO. Pipelines suggests teams and owners from CODEOWNERS, and turns on approvals for Prod now that more than one team ships.
  2. The realtime team's service needs a sidecar and steady background work. They change its runtime to GKE Autopilot. Plans an Autopilot cluster in each project, a namespace for the group, and a traffic shift from Cloud Run through the front door. It shows the monthly cost difference before anything happens.
  3. Builds now run all day and Cloud Build minutes add up. Pipelines suggests a runner pool and shows the saving. They accept. Creates an Autopilot runner pool in the CI project, with a warm cache, that scales to zero at night.
  4. They want Staging separate from Dev. They switch the layout to Standard. Creates a Staging project, redeploys Staging there, and drains the shared one.
  5. Pipelines asks each team to set tiers. The payments services become Tier 0, which adds a second approver and a canary in Prod.

None of these steps changed a service's own file except the runtime line, and none needed a new system.

An enterprise attaches what it has

Who 500 engineers, 50 teams, a platform teamHas 300 projects made with Terraform, GKE Standard clusters, GitHub Actions in 800 repositoriesGoal One way to release to Prod, with audit, without moving builds first
  1. The platform team installs Bemmoly on an existing cluster with Helm, and connects SSO and SCIM so teams sync from the identity provider.
  2. They attach their existing projects to environments. Pipelines writes the grants it needs as a Terraform module, so the change goes through their own review and their own apply. Needs a deployer role per project, and namespace rights per cluster, nothing more.
  3. Discovery reads all 800 repositories and proposes the catalog: domains, groups, applications and owners. Teams review and accept their own.
  4. A campaign opens one pull request per repository adding the release step to each GitHub Actions workflow. Builds stay where they are.
  5. Security sets policies: Tier 0 needs two approvers, nothing ships in a freeze, and only people may approve, never tokens or agents. Every refusal says why and who to ask.
  6. A new product line starts. The platform team marks a new folder as managed, and Pipelines creates its projects in the Enterprise layout. The old world stays attached.
  7. Months later, teams that want faster builds move them onto Pipelines' runners, one pipeline at a time.

Moving clouds

This is the case behind Pipelines: a company moving from AWS to Google Cloud, service by service. It needs the AWS provider, so it lands after Google Cloud is proven.

  1. Attach the existing AWS accounts in deploy-only or attached mode. Pipelines starts deploying there without changing anything.
  2. Add Google Cloud environments to the same release path, so one release can go to both.
  3. Move each service by shifting traffic between the two clouds at the front door, with a canary and a way back.
  4. Retire each AWS environment once nothing points at it. Data stores move on their owners' plans, which Pipelines lists but never runs.

Three things stand out:

  • None creates a project or account per environment. Almost all of them work inside a single project or account, which is where an enterprise's separation between Dev and Prod starts.
  • The category is unstable. In about two years, Argonaut, Coherence and Zeet stopped or pivoted, Flightcontrol rebranded, and Zeabur is shutting down after a breach. A hosted service that holds admin rights to a company's cloud is a real risk. An open-source control plane in the company's own project removes it.
  • Demand is moving. Heroku stopped new feature work in February 2026, and AWS closed App Runner and Proton. Teams on those platforms are looking for a home on their own cloud.

What to copy

  • Render's blueprint file. The easy path writes a real file the team can read and edit, so growing never means starting over.
  • Harness's model of service, environment and infrastructure. It is the clearest answer to "where does this run", but Pipelines keeps it out of sight until a company needs it.
  • Kargo's registry watching. A team can adopt only promotions by letting Pipelines notice new images, without touching its CI.
  • Cloud Deploy's parallel targets. One environment can deploy to several targets at once, such as two regions.
  • env zero's guardrails on self-service. Preview and test environments carry a time to live and a budget cap.
  • Octopus's default environments, trimmed. Start with a preview and Prod, and add Staging when a second long-lived environment is needed. Three environments on day one is heavy for three engineers.
  • Porter's cost estimate before anything is created, and its automatic quota requests.
  • Qovery's rules that stop idle environments, for previews and test environments.
  • Ravion's import of existing resources into Terraform state, for attached mode and for export.
  • Plural's scan for deprecated Kubernetes APIs before every upgrade, for clusters Pipelines runs.
  • Northflank's release flows, where a promotion can back up a database before it deploys.

Where to be different

  • Open source and self-hosted, with nothing held back. Vercel, Octopus and Akuity put SSO, audit or self-hosting in their top tiers. Pipelines keeps them in every install.
  • One system across the whole row. Only Harness and the hosted platforms span build to rollback today, in opposite ways. Pipelines does it on the company's own cloud, with the easy path on top of the full model.
  • No one-way doors. Every choice can be switched with a plan, and everything exports. Most products in this space lock the runtime in at the start.
  • A project per environment, and a runtime per service. No managed-cloud product in this group does both.

Google's own tools

Two Google products overlap. Cloud Deploy promotes releases to Cloud Run and GKE, with canaries and automatic repair, but it assumes the infrastructure exists and works only on Google Cloud. Application Design Center, generally available since December 2025, designs and deploys Terraform-backed application templates and registers them in App Hub. It is the closest Google comes to the managed mode. Pipelines should register what it deploys in App Hub, so a company's Google console shows the same applications, rather than compete with it.
