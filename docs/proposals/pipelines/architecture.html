Bemmoly Pipelines: architecture

How a separate Pipelines product sits on the Bemmoly kernel. It covers how the control plane schedules about 300 concurrent jobs for 500 engineers on a runner fleet in the customer's own cloud, and how releases move through environments under team-based policy. Every cloud-specific part sits behind a provider, so Google Cloud comes first without locking anything to it.

2. Goals and sizing

The design is sized for Acme: 512 engineers, 54 teams, 812 repositories, 1,140 services, three Prod regions. These are the assumptions behind every budget in this document. They are estimates, to be replaced by load-test results.

It must still fit a five-person startup on one VM. The same image runs both, and the difference is configuration and replica count (§19).

3. A separate product

Pipelines lives in the same repository and uses the same kernel. It does not share Bemmoly's web shell, sidebar or navigation, so a person who only has Work and Docs never sees it.

Install modes. BEMMOLY_PRODUCTS=pipelines runs Pipelines alone, with the kernel and none of Work and Docs. BEMMOLY_PRODUCTS=work,docs,pipelines serves both front doors from one install. Hosts are routed by the proxy. Sign-in is shared through the kernel session on a parent-domain cookie, or through OIDC between the two hosts when their domains differ.

What changes in the kernel: a product concept above modules (manifest, host, shell, product grants). Module-level "surface" so a module can be kernel-registered without appearing in Bemmoly's sidebar. Pipelines also needs push detail and the write side (checks, deployments) on code hosts. Each change gets an ADR. The first one is "Pipelines is a separate product with its own shell", which amends ADR 0016's single-frame rule for Bemmoly's product only.

4. Control and execution

  • 1Webhooks, signature checked, written to the inbox
  • 2People and team membership
  • 3Web, CLI and MCP requests
  • 4Runners claim jobs: outbound, long-poll
  • 5Logs, results and test reports stream back
  • 6Deploys, as each environment's deployer
  • 7Landing zones: accounts, networks, identities

Two rules shape everything else. First, runners never deploy to a protected environment. They build, test and publish images. Deploys are done by the control plane, through the provider, as the target environment's own deployer identity. Second, nothing in the execution plane needs an inbound connection. Runners poll out, so they can sit in private networks with no public address.

5. Scheduler and queues

Job dispatch is the hot path, and it gets its own small engine instead of pg-boss. pg-boss is a fine general job queue, but it doesn't do weighted fairness, concurrency groups or superseding. Earlier load tests on Bemmoly also found its default polling too slow for this kind of rate (the 30-jobs-a-minute ceiling in 0.12). It stays for the control plane's own background work.

5.1 The queue

A table pipeline_jobs holds every job, with state (pending, ready, claimed, running, done), pool, team_id, priority_class, concurrency_key and ready_at. A job becomes ready when its dependencies finish. Runners claim jobs through the dispatcher. Each dispatcher replica runs a loop: it picks the next team by deficit round robin, then claims that team's best ready job for the pool with SELECT … FOR UPDATE SKIP LOCKED LIMIT 1, all in one transaction. LISTEN/NOTIFY wakes the loop when a job becomes ready, so there is no polling delay.

5.2 The rules

RuleMechanism
Fair share by teamWeighted deficit round robin per pool. Weights come from Platform › Capacity. Idle share can be borrowed and is returned at the next dispatch, never by killing running jobs
Priority classesrollback > deploy > main > pull_request > scheduled. A higher class skips fair share entirely, and a roll back never waits
Concurrency groupsconcurrency_key such as deploy:checkout-api:prod-asia. At most N running per key (1 for deploys). Others wait in order
SupersedingA new run with the same supersede_key (a pull request number, or a release waiting for an environment) cancels pending and running jobs of the older run. Deploys already shifting traffic are never cancelled mid-step
DeduplicationAn idempotency key per webhook delivery and per commit and service, so a redelivered webhook starts nothing new
Timeouts and lost runnersRunners heartbeat every 10 s. Missing three beats returns the job to ready with attempt + 1, at most twice. Job timeouts come from the pipeline (default 60 min)
Autoscaling signalReady jobs and their wait per pool are exported to the runner autoscaler (§6), which scales on queue depth instead of CPU

5.3 Throughput

A claim is one indexed read and one update. On a 4 vCPU Postgres, the target is 50 claims a second with p99 under 50 ms. The 75,000 jobs a day are small for Postgres. pipeline_jobs and pipeline_steps are range-partitioned by month, so old partitions detach to cold storage without vacuum pain. The exact numbers come from a load test before phase 2, the same way Bemmoly's capacity page was measured.

6. Runners

  • One binary, bemmoly-runner (image ghcr.io/bemmoly/runner). It registers to a pool with a pool token. Then it long-polls POST /api/v1/runner/claims over HTTPS and receives one job with a short-lived job token, scoped to that job and expiring when the job's timeout does.
  • Steps run as containers. On Kubernetes, the runner pod runs each step as a container in the same pod, with a shared workspace volume. On a VM, it uses the local container runtime. Docker-in-Docker is never needed: image builds use BuildKit in rootless mode.
  • Ephemeral. One job per runner, then the pod or VM is destroyed, so nothing leaks between jobs or teams. Warm pools keep start-up under 10 seconds.
  • Autoscaling on Kubernetes is a small controller, bemmoly-runner-controller. It reads each pool's queue depth from the control plane and creates runner pods; Autopilot or the cluster autoscaler adds nodes. On VMs, the provider's instance groups or auto scaling groups scale on the same signal.
  • Logs are sent in ordered chunks (about 64 KB or 1 s) to the log service, which appends them to object storage and fans them out to viewers. If the control plane is unreachable, the runner buffers to disk and resends. A job never fails because the UI was down.
  • Caches: image layers in the registry. Dependency caches go to an object store bucket per pool, keyed by lockfile hash. Test timings are kept per test file, so shards finish together.
  • Managed build services (Cloud Build, CodeBuild) are an optional executor for teams that want no cluster on day one. They implement the same Executor interface, with fewer features: no shared warm caches and coarser logs.

7. Pipelines and templates

At 1,000 services, most pipelines should be one line long. The platform team publishes templates (golden paths) as versioned files in a platform repository. Services extend a template and override only what the template allows.

# acme/pipeline-templates/node-service.yaml, tag v3
inputs: { node: { default: "24" }, port: { default: 8080 } }
build:  { dockerfile: Dockerfile }
test:
  - { name: Unit, image: "node:${{ inputs.node }}", run: pnpm test, shards: auto }
  - { name: Security scan, uses: acme/scan@2, locked: true }   # services can't remove it
deploy: { kind: container-service, port: "${{ inputs.port }}" }

# services/checkout-api/.bemmoly/service.yaml
name: checkout-api
system: checkout
owner: team/payments
tier: 0
pipeline:
  extends: acme/node-service@3
  with: { port: 8081 }
  deploy: { resources: { cpu: 1, memory: 512Mi }, secrets: { DATABASE_URL: checkout-db-url } }
  • The schema is zod in packages/shared. JSON Schema is generated from it for editor completion, and bemmoly-pipelines lint runs locally and in pull requests.
  • Resolution happens per commit. The resolved pipeline (template plus overrides) is stored with the run, so a run always shows exactly what it ran.
  • Fleet upgrades are campaigns. Pick a template change and a set of services, and the campaign opens pull requests in waves (for example 50 a day) and tracks merged, failing and ignored. Its view is the "612 on v3" list in the product design.
  • Rules that protect environments are not in these files. Approvals, windows and canary requirements come from policy (§10). A file can ask for more caution, never less.

7.1 Bring your CI

Companies keep GitHub Actions, Jenkins, Buildkite or anything else for build and test. Pipelines takes over from the built image. It is the third Executor, and the one most large companies start with:

  • Registering a release. POST /api/v1/pipelines/releases takes a service, an image digest, the commit, and optional test reports and attestations. The bemmoly/release GitHub Action and bp release create both call it.
  • No stored secret for GitHub Actions. The action sends the workflow's own OIDC token. Pipelines verifies it against GitHub's issuer, then maps its claims (repository, ref, workflow_ref, environment) to services through a trust rule per repository. A workflow can only register releases for services in its own repository, from refs the rule allows. Other CI systems use a scoped token per pipeline, or their own OIDC where they have one.
  • Their results become gates. Pipelines reads check_run and workflow_run events for the commit. A policy can require "workflow security.yml passed" as a gate. Test reports in JUnit format are stored with the release and shown on the Promote screen.
  • Provenance. If the workflow produces a build attestation (GitHub artifact attestations or SLSA provenance), Pipelines verifies it and stores it with the release. Prod policies can require it.
  • The run view stays complete. An external run is drawn from the forge's API: its jobs, status and timings, with links to the full logs. The journey from commit to Prod is one line, even though the build happened elsewhere.
  • Moving builds later means adding pipeline: to service.yaml. Steps can call the same scripts (run: make build). A converter for GitHub Actions workflows handles the common cases (checkout, setup actions, run steps, caching) and lists what it could not convert. It never claims a full conversion.

8. GitHub at scale

  • One GitHub App per install, on the whole organisation. The kernel's one-click app manifest flow creates it. Pipelines adds write permissions: checks, statuses, deployments, contents (for bot pull requests) and merge groups.
  • Durable ingest. Each delivery's signature is verified, then the delivery is written as-is to webhook_inbox, and the request returns 202 within 50 ms. Workers process the inbox in order per repository. A burst of 2,000 deliveries after an outage queues up instead of timing out GitHub's 10-second limit. Redeliveries are deduplicated by delivery id.
  • Rate limits. An installation token's limit scales with the organisation's size, up to about 12,500 requests an hour. Pipelines caches with conditional requests (ETags), batches reads through GraphQL, reports checks once per job state change (never per log line), and keeps a per-installation token bucket so a fleet campaign can't starve live runs.
  • Merge queues. merge_group events run the required pipeline on the queue's temporary branch, and the result is reported as the required check.
  • Unreachable installs get the relay from draft 1. A small function in the customer's cloud accepts GitHub's POST and puts it on a queue the control plane pulls from. The relay holds no secret, so it cannot forge deliveries.
  • Other forges (GitLab, Bitbucket) come through the kernel's code-host interface. Pipelines never imports a forge client directly.

9. Catalog and ownership

  • Discovery is a job per repository. It runs when the app is installed, on repository events (created, renamed, archived, transferred), and nightly. It finds deployables: Dockerfiles, Helm charts, serverless manifests, and workspace members from pnpm, npm, Nx, Turborepo, Go modules, Cargo, Gradle and Bazel. It reads CODEOWNERS and existing catalog files (including Backstage's catalog-info.yaml), and proposes services.
  • Source of truth is service.yaml in the repository, read on every push to the default branch. Changing ownership is a pull request, reviewed like code. Domains and systems are defined in the platform repository's catalog.yaml, or in the UI, which writes back as a pull request.
  • Teams come from the kernel, synced by SCIM or SSO groups. A service's owner must name an existing team. If it doesn't, the service lands in No owner, which blocks protected deploys.
  • Affected-service detection builds a dependency graph per monorepo: workspace dependencies plus paths filters from service.yaml. The graph is cached per commit. A push maps changed files to the services that need a run.
  • Service dependencies are declared (dependsOn), and optionally learned from traces later. They feed coordinated releases and the "include callers" filter on What changed?

10. Access and policy

10.1 Model

  • Scopes form a tree: organisation, then domain, then system, then service. Environment classes (dev, staging, prod) are a second axis.
  • Role bindings (team or person, role, scope, environment class?) live in pipeline_role_bindings. Bindings to people exist for break-glass only, and they expire.
  • Ownership is implicit. The owning team holds Maintainer on its services without a stored binding.
  • The effective permission set is the union of bindings on the path from the root to the service, for the person's teams. It is computed per (person, service) and cached in process with a version stamp, following ADR 0036 for authorization lookups. Any binding, team or ownership change bumps the stamp.

10.2 Policies

Policies are evaluated for protected actions (deploy, approve, change variables, roll back) on top of roles. They are written in CEL (Common Expression Language, evaluated with a sandboxed TypeScript implementation). CEL is side-effect free, fast, readable, and used by Kubernetes for the same job. Each policy has a selector (which services and environments), a condition, and requirements:

name: Tier 0 to Prod
applies: service.tier == 0 && env.class == "prod"
require:
  requester: has_role("maintainer")
  approvals:
    - { from: owning_team, count: 2, exclude: authors }
    - { from: oncall("sre"), count: 1 }
  gates: [tests, security_scan, staging_healthy("30m"), error_budget("> 0"), canary]
  window: "Mon-Thu 10:00-16:00 Asia/Kolkata"
  deny_if: freeze.active
  • Explanations. Every decision returns a trace: the bindings that applied, each policy matched and the requirement that failed. The trace is stored with the action, and it is what "Why can't I?" and the checker show.
  • Changing policy is itself protected. Policies are versioned. A change to a policy that applies to Tier 0 needs a second Platform admin's approval. Policies can be exported to, and optionally owned by, a Git repository.
  • Inputs are facts, not guesses. Facts such as on-call (from an on-call integration or a schedule in Pipelines), freezes (a calendar) and error budget (from the metrics provider) are resolved before evaluation. If a fact is unavailable, the gate shows "waiting" with the reason. It never shows "pass".

11. Releases and promotion

  • A release is (service, version, image digests per platform, resolved config, provenance, SBOM). It is created when a build on a release branch or tag passes, and never changes afterwards.
  • The environment path per service comes from its tier's path template, for example dev, then staging, then prod-asia, then prod-us and prod-eu.
  • A promotion is a record with a state machine: requested, gating, awaiting_approval, scheduled, rolling_out, then succeeded, rolled_back or cancelled.
  • Gates implement evaluate(release, environment) → pass | fail | pending(reason, recheckAt). The engine re-evaluates pending gates on their recheck time and on relevant events. Gates in phase 1: tests, security scan, staging healthy, window, freeze, approvals. Later: error budget, dependencies released, migration reviewed, custom webhook gate.
  • Release trains are schedules per scope. At the cut time, eligible releases (gates passed) join, the train asks for one approval, and it rolls out in waves with per-service canaries. A failing service is removed from the train and the rest continue.
  • Coordinated releases are a DAG of service promotions with ordering and a failure policy (stop all, or continue the independent ones).
  • Rollout waves span regions. Each wave is a set of deployments with canary steps (§13). A wave starts after the previous one is healthy for its bake time.
  • Change records. Each finished promotion writes an immutable record: what, who requested, who approved, every gate result with evidence, timings, and the outcome. It can be exported as CSV or JSON for SOC 2 and ISO 27001 evidence.

13. Canary and roll back

Each canary step shifts weight, waits, and analyses. Analysis queries MetricsSource for the canary revision and the stable revision over the same window. The built-in checks are error rate and p95 latency, which work without any instrumentation on Cloud Run, ECS behind a load balancer, and Kubernetes with Gateway API metrics. Custom checks are PromQL or the provider's query language. Two failing samples in a row roll the deployment back, mark it rolled_back, record the failing samples, and emit pipelines.deployment.rolled_back. When Bemmoly Work is installed, that event can open an incident. After 100%, a watch period compares against the previous release's baseline, and a failure during the watch also rolls back. This is phase 3. Phase 2 ships manual canaries, with steps and charts, and people decide.

14. Provider model

Everything cloud-specific is behind a provider: one folder of implementations of these interfaces, plus a conformance test kit that every provider must pass against a real test account.

InterfaceResponsibility
ConnectionEstablish and verify keyless identity; report the principal; health check
OrgStructureCreate and read boundaries (folder, organizational unit) and accounts (project, account) inside them
LandingZonePlan and apply an environment's resources: APIs or services, network, registry access, deployer and runtime identities, budget, logging
RegistryRepository per system, pull access per environment, image lookup by digest
SecretsWrite versions, grant access to runtime identities, never read values back
TargetsThe deploy kinds in §12 the provider supports
MetricsQuery per-revision series for canary analysis and health
RunnerHostingCreate and scale runner pools (cluster node pools or instance groups)
AccessGrant and revoke time-boxed console roles to people's cloud identities
CostSpend per account and per label, for the cost views

The landing zone reconciler from draft 1 becomes provider-neutral. Resources are declared as neutral kinds (account, network, registry_access, deployer_identity, budget) and the provider maps each to its own calls. It keeps the same read, diff, apply, verify loop, the same idempotent jobs keyed by spec hash, and the same nightly drift scan. Layouts decide granularity: one account per environment; per domain and environment (the default above 100 engineers); or per system and environment.

Mixed clouds. Each environment names its provider and account, so a release path can be dev (gcp), then staging (gcp), then prod-asia (gcp) and prod-us (aws). One image is built per platform and pushed to each provider's registry by digest. A promotion copies the image to the target's registry first when they differ.

15. Google Cloud provider

This carries over from draft 1, generalised.

  • Bootstrap. One command in Cloud Shell (get.bemmoly.com/gcp) creates the Bemmoly folder and the control project. It installs the control plane on a VM, or prints a Helm command for an existing GKE cluster, and grants the control identity folder-scoped roles plus billing.user and billing.costsManager. An organisation is required, because service accounts can't create projects without a parent.
  • Identity. On Google Cloud: the attached service account. Elsewhere: workload identity federation with a pool whose OIDC provider has Bemmoly's public JWKS uploaded directly, so Google never needs to reach Bemmoly. No key files by default.
  • Per environment, a deployer@ service account with only deploy roles in that project. The control plane impersonates it for every deploy, so the project's audit logs name the environment's deployer. --lock removes the folder's provisioning roles once the landing zone is in place.
  • Runners on GKE Autopilot in a <org>-ci project, by default. They use Workload Identity, and the builder identity can only push to Artifact Registry.
  • Quotas. New billing accounts can link only a few projects. The per-domain layout needs a quota increase, and the connect screen checks that before planning.

16. AWS provider (phase 3)

The AWS provider is designed now so that the interfaces don't bend toward Google:

  • Boundary and accounts: an organizational unit Bemmoly, with accounts created through AWS Organizations (CreateAccount, which needs a unique email per account; Pipelines uses plus-addressing on an admin mailbox). If Control Tower is present, accounts go through its Account Factory instead.
  • Identity: an IAM role per account (BemmolyDeployer) trusting Bemmoly's OIDC issuer. AWS STS fetches the issuer's keys from its public discovery URL. For installs that are not public, Pipelines publishes the discovery document and JWKS to a public S3 bucket, which is the pattern self-managed Kubernetes clusters use for IAM roles. A one-command CloudFormation stack in CloudShell sets this up.
  • Targets: ECS on Fargate (container-service), EKS (kubernetes), Lambda (function). Registry: ECR with cross-account pull. Secrets: Secrets Manager. Metrics: CloudWatch.
  • Runners: EKS with Karpenter, or auto scaling groups. A CodeBuild executor is the no-cluster option.

17. Identity and secrets

  • Jobs get OIDC tokens. Pipelines is an OIDC issuer for its own jobs. A job can ask for a token with claims such as service, env, ref and tier. Clouds trust those claims through federation, so a test job can read a staging bucket without any stored secret. The issuer's discovery document is served publicly, or uploaded where the cloud allows it.
  • Application secrets live in each provider's secret store, in the environment's account. Pipelines stores references and versions, never values. Values are written straight through to the provider and masked in logs.
  • Build-time secrets are mounted only into the steps that name them. Pull requests from forks get none and wait for a maintainer.
  • Pipelines' own secrets (signing keys, the GitHub App key) are sealed with the kernel's secret box. Signing keys rotate from the UI, with overlap.

18. Live views and history

  • Streams. The web app opens one server-sent events stream per tab and subscribes to topics: a scope's map, a run, a service, the person's For you. The server coalesces updates to at most one per topic per second. For 400 viewers that is a few hundred small messages a second, fed by Postgres NOTIFY from the writers.
  • Logs come from the log service. While a job runs, its chunks are kept in memory on the replica that receives them, fanned out to subscribers on any replica through NOTIFY with a pointer, and appended to object storage. Search inside a log reads ranges from object storage on demand. Logs are not indexed.
  • The Release map reads a materialised table, pipeline_current: the current release, deployment state and moving releases per (service, environment), updated in the same transaction as each deployment event. Counts per (scope, environment) are computed from it, which takes milliseconds for 1,140 services.
  • Rewind. Every deployment state change is an append-only row in pipeline_deployment_events, so the state at time T is the latest event per (service, environment) at or before T. An hourly snapshot plus the events since keeps rewind under 200 ms for any point in the last 90 days.
  • Insights (lead time, deploy frequency, change failure rate, time to restore) are computed nightly into daily rollups per service, then aggregated up the catalog tree.

19. Availability and upgrades

  • Leader-only work (cron triggers, train cuts, the drift scan) takes a Postgres advisory lock. Everything else runs on every replica.
  • If the control plane is down, runners finish their jobs and buffer logs. Deploys already in progress at the provider complete or stay where they are, because traffic weights live in the provider and not in Pipelines. On return, watchers reconcile actual state from the providers before acting.
  • Upgrades follow Bemmoly's rules: expand and contract changesets, compatible with the previous minor version, and rolling restarts. The runner protocol is versioned, and the control plane supports the current and previous runner minor versions.
  • Backups use the kernel's Postgres backups. Logs and artifacts follow object-storage lifecycle rules: 30 days hot, then deleted or archived by setting.

22. API, CLI, MCP

  • REST under /api/v1/pipelines/…, following the repository's API rules: plural nouns, keyset pagination, one level of nesting, the standard error body. Live streams use /api/v1/pipelines/streams (server-sent events). The runner protocol lives under /api/v1/runner/…, versioned separately.
  • CLI bemmoly-pipelines (alias bp): bp run, bp logs -f, bp promote checkout-api --to prod, bp rollback, bp lint, bp why (explain an access decision). It signs in with device code through the kernel's OAuth server.
  • MCP: read tools for services, runs, logs, releases and what changed, plus write tools (run, promote request, roll back) that go through confirmed plans (ADR 0019) and the person's own access. Approval is never a tool.
  • Chat: approval and failure notifications with Approve and Open buttons. Approving from chat re-checks policy and identity on the server.
