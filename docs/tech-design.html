Bemmoly: technical design

Your work. Your platform. Open source, self-hosted, AI-first issues and docs for your whole company. One app image, one Postgres, deployed in five minutes, free forever.

Draft v0.10 7 October 2026 Source of truth for product scope: docs/design/*.dc.html (14 screens) Engineering contract: engineering-standards

1. Summary and the eight promises

Bemmoly is two products in one deployable: Work (projects, issues, boards, sprints, roadmap, workflows) and Docs (spaces, pages, a collaborative editor), joined by a single AI layer that reads both and acts through the same permissions a person has. The design mocks fix the experience; this document fixes how it is built.

Every technical decision below was tested against eight promises taken straight from the landing page and the setup wizard. If a decision breaks a promise, the decision loses.

Promise 1
5 min
curl to first login on a fresh VM. The installer owns Docker, Postgres, HTTPS, backups and upgrades.
Promise 2
1 + 1
One application image plus one Postgres. No Redis, no Elasticsearch, no message broker, no object store required.
Promise 3
2 vCPU · 4 GB
Runs a 200-person company. Every subsystem is sized for this box first and scales out second.
Promise 4
$0 / seat
MIT licence, no seat limits, no feature gating, no phone-home unless the admin opts in to update checks.
Promise 5
Any AI, or none
Anthropic, OpenAI, Azure, OpenRouter, Ollama, vLLM. Nothing leaves the server until a provider is connected.
Promise 6
Plan → confirm → run
AI never mutates data silently. It proposes a plan, a person confirms, it runs under their permissions and lands in the audit log.
Promise 7
1 cmd
Upgrade and rollback are single commands. A backup is taken automatically before every upgrade.
Promise 8
Imports
Jira and Confluence imports keep keys, history, comments, attachments and page trees so migration is a background job, not a project.

3. Architecture

Bemmoly is a modular monolith. One Node process serves the API, the WebSocket endpoint, the collaborative-editing endpoint, the static SPA and the background workers. The same image can be started with BEMMOLY_ROLE=api or BEMMOLY_ROLE=worker to split it across machines when a deployment outgrows one box. Nothing in the code knows or cares which mode it is in.

Request path

A request enters through Caddy, hits a Fastify route that does nothing but name a controller, the controller validates input with a zod schema from the shared package and calls one service function, the service checks authorization and does the work through Drizzle, and a single error handler maps typed errors to status codes. Anything slow goes to the job table instead of the request. Any change that other clients should see is published on a Postgres channel and fanned out to WebSocket subscribers, who invalidate their query cache rather than receiving the data itself.

Why a monolith and not services
A 200-person company on a 4 GB VM cannot afford the memory of six processes, the operational surface of a service mesh, or the network hops. Module boundaries inside services/ are enforced by lint rules (no cross-module imports except through each module's index.ts), which gives the maintainability benefit without the deployment cost. If a module ever needs its own process, it already has a clean seam.

4. Modules

Question asked
Can Work and Docs be separate modules, so a team can install only Docs, only the board, or any mix, and so future capabilities can be added the same way?
Decision
Yes. Bemmoly is a small core kernel plus installable modules. Every product capability (work, docs, and anything that comes later) is a module that plugs into the kernel through a fixed contract. Modules ship inside the one application image and are switched on per install; the image stays one artifact so the five-minute install and one-click update promises hold.
Why one image
Downloading module code at runtime means a version-compatibility matrix, signature checks, a plugin loader and a second update path, all before 1.0 ships. Shipping every module in the image and enabling by configuration gives the install-only-Docs experience today and keeps the door open for separately distributed modules later, because the contract below is the same either way. GitLab works this way: one version, many optional features.

The module contract

A module is a package that exports one manifest. The kernel loads enabled modules in dependency order at boot and asks each one to register what it provides. Nothing else in the kernel knows a module's name.

// packages/core/src/modules/contract.ts
export interface BemmolyModule {
  id: 'work' | 'docs' | string;        // stable, lowercase, used in config, URLs and the changelog table
  version: string;                     // the app version it shipped in
  coreApi: string;                     // semver range of the kernel API it was built against
  dependsOn?: string[];                // hard dependencies on other modules (a future service-desk needs work)
  defaultAccess: 'everyone' | 'teams' | 'none';  // initial module_grants row when enabled (§4, who can see a module)
  changelog: Changelog;                // this module's ordered changesets, tracked per module in schema_changelog
  register(ctx: ModuleContext): void;  // everything below happens here, at boot
}

export interface ModuleContext {
  routes: RouteRegistry;               // mounts under /api/v1/<resource>, same route→controller→service layering
  entities: EntityRegistry;            // declares entity kinds ("issue", "page") with a resolver, a renderer id, a search document builder, an ACL check
  links: LinkRegistry;                 // link kinds this entity participates in (mention, embed, blocks)
  capabilities: CapabilityRegistry;    // capability names for the roles matrix, with defaults per system role
  navigation: NavRegistry;             // top-nav entries, settings panels, ⌘K groups, create-menu items
  jobs: JobRegistry;                   // job handlers and schedules
  events: EventBus;                    // publishes domain events; other modules may subscribe by kind, never by import
  search: SearchRegistry;              // indexers and LQL fields
  ai: AiRegistry;                      // tools, context builders, insight generators, prompt files
  editor?: EditorRegistry;             // nodes and slash commands, when the docs module is enabled
  importers: ImporterRegistry;         // importer implementations
  settings: SettingsRegistry;          // module-scoped settings schema (zod) and defaults
}

Rules that make modules real

  • No module imports another module. Enforced by the same ESLint boundary rule as the layering. Cross-module behaviour goes through kernel registries and events. The test that proves it: the integration suite boots the server three times, with work only, docs only, and both, and runs each module's tests in the configurations where it is enabled.
  • A module owns its tables. Core tables carry no module-specific columns. Where the kernel needs to reference module data (links, notifications, audit, search), it stores entity_kind plus entity_id and asks the registry.
  • Shared behaviour lives in the kernel, not in the first module that needed it. Comments, attachments, reactions, watchers and labels are kernel services keyed by entity kind, so a future module gets them for free.
  • Optional dependencies degrade visibly. Docs' "Linked issues" panel, Work's "Linked docs" panel and the AI consistency check exist only when both modules are enabled; the UI says what is missing and how to enable it.
  • The kernel is the only thing with a global changelog run. Enabling a module later runs its changelog under the same advisory lock; disabling a module unregisters it but keeps its tables until an admin explicitly chooses "remove data", which is a confirmed, backed-up, audited action.

Who can see a module

Enabling a module for the workspace and letting a person use it are two different decisions. Engineering may have Work, everyone may have Timesheets, and a contractor may have only the Docs space they were invited to. So authorization has three layers, evaluated in this order by the authz service:

Mobile

Same answer for the same reasons: one app named Bemmoly, not one per module. It reads the module manifest from the server and shows only the modules the person can access, so a Docs-only workspace gets what looks like a docs app. One store listing, one login, one push-notification registration, deep links that cross modules (bemmoly://work/PLT-204). Sequencing: the SPA ships as an installable PWA with web push for 1.0, which covers inbox, approvals, comments and timesheet entry on a phone; a native shell (Expo) follows after 1.0 and loads module screens by manifest, so adding a module never means shipping a new app. Separate apps per module is listed in §25 as the rejected alternative.

Versioning

For 1.x every module ships in the image and carries the application's version, so an update moves everything together and there is exactly one compatibility question: does this image's kernel support the database it finds. Module manifests already declare the kernel API range they need, and changesets are tracked per module, so the 2.0 question of separately distributed, separately versioned modules (a community module installed from a registry, signed and sandboxed) is a packaging and trust problem, not an architecture change. It is listed in §25 rather than promised.

Rules that keep it clean

  • Services never import routes or controllers. Enforced by an ESLint import/no-restricted-paths rule, so a violation fails CI rather than code review.
  • Modules talk through the kernel. A module imports @bemmoly/core and nothing under modules/. Inside the kernel, each service folder exposes an index.ts and internal files are private.
  • Every file is 300 lines or fewer. A lint rule, not a guideline.
  • One schema, one place. A request body's zod schema lives in packages/shared, is used by the controller to validate and by the web form to validate, and generates the OpenAPI document. Nobody writes the shape twice.
  • Typed errors only. NotFoundError, ForbiddenError, ValidationError, ConflictError, RateLimitedError, ProviderError. The error handler in middlewares/error-handler.ts owns the mapping to status codes; no controller writes a status code by hand.
  • Pluggable capabilities (AI, email, storage, importers, SSO, automation actions) always use interface + factory + one file per implementation. Adding a provider is one file plus one registry line plus config.

7. Database

Question asked
Postgres or Mongo? Can we give users the option?
Decision
PostgreSQL only. The option Bemmoly gives users is where Postgres runs, not which database it is.
Why
  • The data is relational to its core: issues ↔ sprints ↔ epics ↔ workflows ↔ boards ↔ pages, with foreign keys, uniqueness (one issue key per project), and transactions (moving an issue updates its status, history, sprint counters and the search index together).
  • Postgres replaces four other services: full text search (tsvector), vectors (pgvector), job queue (pg-boss) and pub/sub (NOTIFY). That is what makes "one container, one Postgres" possible. Mongo cannot do that.
  • Supporting two databases means two migration sets, two query layers, two test matrices and two sets of bugs, forever. It is the single most expensive thing an open source project can take on, and the mocks' landing page already promises "Postgres only".
  • Mongo's one genuine strength, schemaless documents, is covered by JSONB columns for custom fields and editor content, with indexes on the paths we query.
Options we do give
Bundled (installer runs pgvector/pgvector:pg18 next to the app; default) · External (RDS, Cloud SQL, Neon, Supabase, your own cluster: set DATABASE_URL, the installer skips the bundled one) · Air-gapped (bundled image inside the offline tarball). The setup wizard's health check reports which one it found, version, latency and whether pgvector and pg_trgm are available.

Conventions

  • Database name bemmoly_db. Tables snake_case plural, columns snake_case. API layer maps to camelCase in the shared schemas.
  • Primary keys are UUIDv7, generated by Postgres 18's built-in uuidv7() as the column default (time-ordered, so B-tree inserts are sequential and pagination by id is chronological). Issue keys like PLT-204 are a separate unique column allocated from a per-project counter row locked with SELECT … FOR UPDATE.
  • Every table has created_at, updated_at. Soft delete (deleted_at) only on issues, pages and comments, because users expect a trash; everything else hard-deletes with cascading foreign keys.
  • Indexes are declared in the Drizzle schema and land in the same changeset as the table. Partial indexes for the hot paths (open issues per project, pages per space not deleted).
  • Schema changes are changesets in a per-module changelog, applied at boot under a Postgres advisory lock so multiple replicas starting at once cannot race. The model and the runner are described in §7.1 below.
  • Editor content is stored three ways on purpose: the Yjs update log (truth for collaboration), a ProseMirror JSON snapshot (for rendering, embeds and exports), and extracted plain text (for search). The snapshot and text are derived and rebuilt by a job if ever missing.

7.1 Schema changelog, Liquibase-style

A folder of numbered SQL files is enough for one app with one schema. Bemmoly has a kernel and several modules, each owning tables, each enabled at different times, and contributors who need to ship data backfills as well as DDL. That is the problem Liquibase and Mongock solve, so Bemmoly adopts their model: an ordered changelog of changesets, each with a stable id, an author, a checksum, optional preconditions and an optional rollback, tracked in a table the runner owns. The runner is a small kernel service in TypeScript, not the Liquibase binary, for the reasons in the stack table.

// modules/work/changelog/0007-issue-rank.ts
import { changeset, sql } from '@bemmoly/core/changelog';

export default changeset({
  id: '0007-issue-rank',                 // stable; the file name must match
  author: 'priya',
  description: 'Replace integer position with a lexorank string for board ordering',
  preconditions: [
    { columnExists: { table: 'issues', column: 'position' }, onFail: 'markRan' },   // already migrated on this install
  ],
  contexts: ['*'],                       // or ['demo', 'test'] for seed data that production never runs
  transactional: true,                   // false for CREATE INDEX CONCURRENTLY, which cannot run in a transaction
  up: async (ctx) => {
    await ctx.exec(sql`ALTER TABLE issues ADD COLUMN rank text`);
    await ctx.backfill('issues', { batch: 5000 }, async (rows) =>      // code changeset: batched and resumable
      ctx.exec(sql`UPDATE issues SET rank = ${lexorankFrom(rows)} WHERE id = ANY(${rows.map(r => r.id)})`));
    await ctx.exec(sql`ALTER TABLE issues DROP COLUMN position`);
    await ctx.exec(sql`CREATE INDEX issues_board_rank_idx ON issues (project_id, rank) WHERE deleted_at IS NULL`);
  },
  down: async (ctx) => {                 // required for DDL-only changesets; optional, and marked irreversible, when data is lost
    await ctx.exec(sql`ALTER TABLE issues ADD COLUMN position integer`);
    await ctx.exec(sql`ALTER TABLE issues DROP COLUMN rank`);
  },
});

Changelog file with changesetsOne changelog/ folder per module (and one for the kernel), one TypeScript file per changeset, ordered by the numeric prefix. The module manifest points at it, which is Liquibase's include.
DATABASECHANGELOGschema_changelog: module, id, author, checksum, executed_at, execution_ms, order_executed, app_version, contexts, state (ran, marked_ran, rolled_back). Rows are never deleted.

Code changesets (Mongock)up is TypeScript. It can run SQL, call ctx.backfill for batched, resumable data transforms with progress logged on the changelog row, or call a kernel service through ctx.services for cases such as re-extracting page text after an editor schema change.

Safety lintingsquawk runs on the generated SQL in CI and blocks a full-table rewrite, a non-concurrent index on a large table, or a NOT NULL added without a default. The release manifest lists any changeset the lint flagged as slow so admins see it before clicking Update.

Runner rules

  • Order: kernel changelog first, then enabled modules in dependency order. Inside a changelog, by numeric prefix; a gap or duplicate fails validation.
  • Boot behaviour: in the default install the app runs pending changesets at boot before it answers /readyz. In Helm deployments a pre-upgrade hook job runs them so pods never start against an old schema; BEMMOLY_DB_AUTO_MIGRATE=false turns the boot run off for operators who prefer that.
  • Transactions: each changeset runs in its own transaction unless it declares transactional: false, in which case the runner writes a "started" row first so a crash mid-way is visible as such rather than as "pending".
  • Compatibility window: a changeset must be compatible with the previous minor release's code (expand first, contract in a later release), so an updater swap or a rolling Helm upgrade never runs old code against a removed column.
  • Module enable and disable: enabling runs that module's changelog from its first pending changeset. Disabling runs nothing. "Remove data" runs the module's down changesets in reverse after a backup, or drops the module's tables where a changeset is irreversible, and records it in the changelog and the audit log.
  • Tests: the integration suite applies every changelog from empty, validates checksums, runs each down and then up again, and applies the changelog on top of a database restored from the previous release's fixture. A changeset without a passing round trip does not merge.

Conventions

  • OpenAPI 3.1 document generated from the zod schemas at build time and served at /api/v1/openapi.json; packages/api-client is generated from it.
  • Keyset pagination everywhere (cursor + limit, max 200). Offset pagination is not offered because it degrades on large backlogs.
  • Responses carry ETag; writes accept If-Match so two people editing the same issue get a 409 instead of silent overwrite.
  • Errors are one shape: { code, message, details?, requestId }. Codes come from the shared enum so the web app can map them to copy. Routes of a module the actor cannot access answer 403 module_access_denied; routes of a module that is not enabled answer 404 module_not_enabled.
  • Idempotency keys on POST endpoints that create (header Idempotency-Key), stored for 24 hours, so retries from flaky networks never double-create.

Realtime

Every mutation in a service ends with realtime.publish({ kind, ids, projectId | spaceId }). The publisher writes a NOTIFY bemmoly_events with that small payload. Every process (api or worker) listens on the channel and forwards to WebSocket subscribers whose subscriptions match (a board subscribes to its project, a page to itself). The client responds by invalidating the matching TanStack Query keys, so the data path is always the authenticated REST API and realtime never bypasses authorization. Presence and cursors for docs ride on Yjs awareness over the collab socket.

Webhooks out

Events (issue.created, issue.transitioned, page.published, sprint.completed, …) are queued per webhook as jobs, signed with HMAC-SHA256, retried with backoff five times, and logged. A built-in "Slack / Teams incoming webhook" template formats the payload for chat tools without a dedicated integration.

10. Authentication, authorization and security

Authentication

  • Password login with argon2id, breached-password check offline against a bundled k-anonymity list is out of scope; minimum length and rate limiting are in.
  • OIDC via openid-client: Google Workspace, Okta, Entra ID and any generic provider share one implementation with per-provider config. SAML via samlify for enterprises that have nothing else.
  • Auto-provision on first SSO login with a default role; IdP groups map to teams; SCIM keeps users and groups in sync and deactivates leavers.
  • "Require SSO for everyone" disables password login except for accounts flagged break-glass, exactly as the People screen shows.
  • Sessions are opaque random tokens in an httpOnly, Secure, SameSite=Lax cookie, hashed at rest, rotated on privilege change, 30-day sliding expiry.
  • Personal API tokens with scopes for scripts and the MCP server; shown once, hashed at rest.

Authorization

  • Module access is checked first (§4): a person without a grant for a module gets module_access_denied before any capability is considered.
  • Capabilities are a closed enum in the shared package. Roles grant capabilities; org admins can lock a row; project and space admins can only remove capabilities below the org ceiling.
  • One function, authorize(actor, capability, resource), in services/authz, called by the service that does the work, never only by the route. The resolved capability set per actor per container is cached in-process for the request.
  • AI plans run through the same services with the requesting user as actor, so every step is checked individually and shown as ALLOWED or DENIED in the plan table before anything runs.
  • Search and the ask-your-docs retrieval filter by container membership before ranking, so a user never sees a snippet from a space they cannot open.

11. AI subsystem

The AI layer is the product's differentiator and its biggest trust risk, so it follows four rules before any feature: off by default, reads through the same permissions as the user, never writes without a confirmed plan, and every call is logged with its cost. The design mocks show AI in three forms, a ⌘K palette, inline suggestions and side-panel insights, and all three sit on the same small set of services.

11.1 One integration: the AI SDK, driven by the models.dev catalog

Principle
Bemmoly has exactly one AI integration in its code: the AI SDK. No file in the repository knows what Anthropic, OpenAI or OpenRouter is. Which provider package to load, which fields to ask the admin for, which base URL to call and which models exist all come from the models.dev catalog at runtime. "Popular providers" is a UI ordering, not code.
Why
  • The AI SDK (npm ai, version 7, Apache-2.0) already is the pluggable-capability pattern the standards contract asks for: one LanguageModel and EmbeddingModel specification, a provider package per vendor, a registry addressing any model as provider:model, middleware, structured output on zod, tool calling, streaming and OpenTelemetry.
  • models.dev is an MIT, community-maintained catalog (SST, used by OpenCode) of 226 providers and roughly 8,400 models. Each provider entry names its AI SDK package, its API key variables, its base URL, docs and logo; each model entry carries capabilities, limits, prices and status. It is the data the UI and the runtime need, so Bemmoly maintains none of it.
  • Adding a provider therefore means nothing in Bemmoly. A new catalog entry appears in the picker on the next refresh. A new vendor-specific package is one dependency bump.
  • The one cost is churn: the SDK ships a major version roughly yearly. A thin facade in services/ai/runtime is the only code that imports it, so a major upgrade is a one-folder change.

How a provider connects, end to end

  1. Pick a provider. The picker shows the catalog with logos. A "Popular" row at the top (an ordered list of catalog ids in overrides.ts, shown with the catalog's own names and logos: OpenAI, Anthropic, Amazon Bedrock, Azure, Vertex and OpenRouter, plus "Local server") makes the common case one click; these six are the providers enterprises most often already have contracts and keys for, and OpenRouter covers everyone else with one key. Below it, every provider in the catalog is listed in full, searchable and sorted by name, with the same logo treatment. The long list is the product, not a fallback hidden behind a link.
  2. Enter what the provider needs. The form is generated from the catalog entry's env list: one secret field per key it expects (an API key for most; resource name plus key for Azure; access key, secret, region for Bedrock), the base URL from api pre-filled and editable, a link to the provider's docs. Values are encrypted with the install's secret key before they reach the database and are write-only afterwards.
  3. Test the connection. Bemmoly loads the package named in npm, builds the provider with those values, and makes one cheap call. Success or failure is reported in plain words with the provider's own error message.
  4. Pick models per role. For fast, standard, strong and embedding, the picker lists that provider's models from the catalog with capability badges, context size, price per million tokens and release date, filtered to models that qualify for the role (planning needs tool calling) and with the suggested default pre-selected. Any provider's model can fill any role, so a local model for fast and a hosted one for strong is one screen.
  5. Use. Services call the facade with a role and a purpose. The facade resolves the role to a registry id, wraps the model in the middleware stack, runs the call through the SDK, validates structured output and records the ai_runs row with cost from the catalog's prices.

Custom endpoints: what the catalog does not list

Ollama, vLLM, llama.cpp and corporate gateways are not in the catalog because their models are whatever the operator loaded. "Local server" in the picker takes a protocol (OpenAI-compatible or Anthropic-compatible), a base URL on the private network and an optional key, discovers models from the server's own model list, probes tool calling and structured output with one request each, and stores the result as a private catalog entry so the same role picker works. Embedding models are thin in the catalog, so a small curated list in overrides.ts fills that role.

Live catalog first, bundled list as the fallback

New models should appear in the picker the day they exist, with no Bemmoly release and no admin action. So the catalog is live by default, and the copy baked into the image is only what Bemmoly uses when the live source cannot be reached. Resolution order, every time the picker or a provider form opens:

  1. Live. The Bemmoly server (never the browser) fetches models.dev/api.json with the stored ETag and a two-second timeout. A 304 or a fresh body refreshes the stored snapshot; a fresh body within the last hour is reused without a request. Logos are fetched the same way on demand and cached.
  2. Last good snapshot. If the fetch fails or times out, the most recent snapshot in ai_catalog_snapshots is used, whether it came from an earlier live fetch or an admin upload.
  3. Bundled. If no snapshot has ever been stored, the JSON and logos baked into the image at build time are used. Every Bemmoly release refreshes that copy.
  • The UI always says which it is. A status line on the picker and on Settings › AI reads "Live · models.dev · updated 4 minutes ago", or "Offline · last fetched 2 October 2026", or "Offline · bundled with 1.2.0". An admin can upload a newer catalog file from any machine that can reach the site, and the air-gapped bundle includes the current one.
  • AI calls never depend on the catalog being reachable. Role assignments store the model id and a capabilities snapshot; the facade reads those from the database. A blocked VPC or a models.dev outage affects only how fresh the picker is, never whether summaries, plans or search work.
  • The daily job stays, now as a background warmer: it refreshes the snapshot even when nobody opens the picker, and flags configured models the catalog has marked deprecated, suggesting the successor from the same family.
  • Privacy. A live fetch is an outbound request from the server to models.dev that carries no workspace data beyond the request itself. It is on by default because it is what keeps the picker current, and an admin can turn it off, in which case Bemmoly behaves as permanently offline for the catalog and relies on uploads and releases.
  • If the provider itself is also unreachable in such a network, that is a separate matter, and what the Local server path and the None option exist for.

Two small mock changes follow from this: the wizard's AI step shows the popular row plus the full, searchable, logo-bearing catalog beneath it rather than four cards, and Settings › AI gains the catalog status line and upload control.

Model roles, not one model
Tasks differ by an order of magnitude in cost and latency need. fast handles ghost text, field suggestions, classification and title cleanup where 300 ms matters. standard handles summaries, briefs and Q&A. strong handles plans for the command palette, forecasts and drafting whole sections. Admins map each role to a provider and model in Settings › AI, and can mix vendors: a local model for fast, Anthropic for strong.

11.2 Prompt management

  • Prompts are Markdown files in the repo with frontmatter: id, version, role, variables, output_schema (zod id) and a short description. They are loaded at boot, validated (every variable used must be declared) and exposed read-only in Settings › AI › Prompts, where an admin can override one; the override is stored in ai_prompt_overrides with a diff view and a "reset to default".
  • Every ai_runs row records prompt_id, prompt_version and the hash of the rendered input, so a bad output can be reproduced and a prompt change can be measured against the feedback column.
  • Structured output everywhere: insights, plans and field suggestions ask for JSON matching a zod schema, validated on return; one repair attempt, then a typed failure. The UI never renders unvalidated model text as data.
  • The system prompt is stable per purpose, the volatile context goes in the user turn, which is what makes Anthropic prompt caching effective.
  • Evals live in apps/server/test/ai/: a fixture dataset (the Acme Labs sample from the mocks) and golden checks per prompt (summary cites at least one source, plan touches only issues named, consistency check finds the planted 15-versus-30-minute conflict). They run in CI against a recorded provider and nightly against a live one.

11.4 Plan → confirm → run

  • Tool definitions in services/ai/tools/ are generated from the same zod schemas as the API, so the model's arguments are validated exactly like a request body.
  • Read tools (search, get issue, list sprint) execute during planning so the model can look things up. Write tools are recorded, not executed, and become plan steps.
  • Each step is checked with authorize() as the requesting user and marked ALLOWED or DENIED. A plan with a denied step can still run its allowed steps if the person chooses.
  • Execution is a job so a 40-step plan survives a page refresh; progress streams back over the WebSocket. Steps are idempotent via the plan id and step index.
  • Comments written by a plan are attributed "via Bemmoly for Rohan", the AI accent colour is used wherever the model produced content, and the audit row links to the plan.
  • "Let AI actions change data" off (Settings › AI) turns the palette into a read-only assistant that still answers and still drafts, but never produces a runnable plan.

11.5 Insight caching and triggers

Summaries and briefs are expensive if regenerated on every view. The ai_insights cache keys on target plus a hash of the inputs the builder used. On view, the service compares hashes; if unchanged, it returns the cached content in under 10 ms. If changed, it returns the stale content immediately with a "refreshing" state and enqueues a regeneration job, which publishes a realtime event when done. Background triggers keep caches warm where it matters: the sprint pulse refreshes after a quiet period of five minutes following any change in the sprint; the morning brief is built by a scheduled job per user at their local 6 a.m.; consistency checks run after a page is published or a linked issue changes.

11.6 Privacy, cost and failure

  • Share content off means builders include titles, keys, statuses and field values but no description, comment or page body. Every builder honours it; a test asserts no body text escapes when it is off.
  • Excluded spaces and projects are filtered at the builder and at indexing time, so excluded content is never embedded either.
  • Optional email and name redaction replaces addresses with stable placeholders before sending and restores them in the output.
  • A monthly budget in USD computed from ai_runs and a per-model price table in presets.ts. At 80% a warning goes to admins; at 100% the standard and strong roles pause and the UI explains why in plain words.
  • Provider failures (the SDK's typed API call errors, normalised by the facade into ProviderError) surface as honest copy ("Anthropic returned a rate limit; I'll retry in 30 seconds") and never block the non-AI path of the screen.
  • Per-user opt-out, when the admin allows it, hides AI surfaces for that user and excludes their authored content from being sent for summaries that other users request, except titles.

12. Email, notifications and pinging

"Pinging" in Bemmoly means three channels fed by one event stream: the in-app inbox, email, and outgoing webhooks (including chat tools). A notification service turns domain events into per-user notifications according to preferences, then each channel delivers on its own schedule.

Email

  • Configuration lives in settings (host, port, security, username, encrypted password, from address, reply-to) and is edited in Settings › Email and notifications or the setup wizard's health check "Configure" action. A "send test email" button is mandatory; it reports the SMTP conversation's failure reason in plain words.
  • Provider pattern: EmailSender interface with smtp (nodemailer) and log (development, writes to the logger and a local mailbox page at /dev/mailbox). SES, Resend or Postmark become one file each if a user needs them.
  • Outbox: services never send; they insert into email_outbox inside the same transaction as the change that caused the mail. A worker drains the table, retries with backoff, and marks failures so admins see "12 emails failed since Tuesday: authentication rejected" instead of silence.
  • Templates are react-email components in services/email/templates/, rendered to HTML and text, themed with the workspace brand colour and logo. Every email has a one-line reason ("You're receiving this because you watch PLT-204") and a per-kind unsubscribe link that updates preferences without login.
  • Digests: mentions, assignments and review requests go immediately; everything else is batched per user every ten minutes into one email, and optionally into a daily summary at the user's chosen hour.
  • Deliverability: the SMTP test checks SPF and DMARC for the from-domain and shows a warning with the DNS records to add. List-Unsubscribe headers on every notification.
  • Inbound email (reply to comment) is a later milestone; the outbox and template layers are designed so it slots in as a job polling IMAP.

In-app inbox

Notification rows are written in the same transaction as the event and pushed over the WebSocket; the inbox badge in the top bar is a query key invalidated by that event. Grouping ("Aisha and 2 others commented on PLT-204") is done at read time so writes stay simple.

14. Work engine

Schemes and overrides

Issue types, fields, workflows and board config exist at org level as defaults and can be overridden per project. An override is a full copy with a pointer to its origin, which is what the "Reset to org default" and "View diff" controls act on. Org locks are rows in the capability matrix, not special cases in the code.

Workflow engine

A transition is allowed if the actor's role is in the target status's allowed roles, every condition passes (field set, subtasks done, linked issues resolved, custom query), and every validator accepts the submitted fields. Post-actions run after commit (assign to reporter, clear sprint, set resolution, fire automation). Conditions, validators and post-actions are entries in a registry keyed by name, so contributors add one by adding a file.

Ordering

Board columns and backlog use a lexorank string column so a drag writes one row, not a renumbering of the list. Rebalancing is a housekeeping job when ranks grow long.

Sprints and metrics

Velocity, burndown, cycle time and throughput are computed from issue_history and the sprint's completion snapshot, cached in ai_insights-style rows keyed by sprint, and recomputed by the quiet-period job. No nightly rollups that are stale by morning.

Custom fields

Definitions in fields, values in issues.custom_fields JSONB. Marking a field filterable creates an expression index in a migration generated by the service. The query language resolves field keys to JSONB paths with the right cast.

Automation

Trigger (event or schedule), conditions (query language), actions (registry: transition, assign, comment, set field, notify, webhook, create subtask, ask AI to draft). Rules run in-process synchronously for conditions and queue their actions. The AI can write a rule from a sentence; it is shown as a draft rule the admin saves.

Roadmap and forecast

Epics carry target dates and dependencies (issue_links.kind = blocks at epic level). The forecast insight feeds the strong model with epic progress, velocity history and dependency graph and asks for a structured answer: projected finish, days late, two or three options with the issues each would move. Scenarios are plans, so "pull Lena from Observability" is a runnable, confirmable set of reassignments.

15. Docs engine

Editor

Tiptap 3 on ProseMirror with a schema in packages/editor shared by the web app (editing) and the server (rendering exports, extracting text, resolving embeds). Custom nodes: issueEmbed (renders live status from the API), issueTable (a saved query rendered as a table), decision, callout, pageLink, mention, codeBlock with highlighting, table, image, toc. Slash commands, /ai commands and ghost-text continuation are editor extensions that call the AI service with a 1.5 s timeout for fast.

Collaboration

Yjs document per page, served by Hocuspocus mounted on the same Fastify server at /collab. Persistence extension writes updates to page_updates and loads page_state; a debounced hook (2 s after the last change) extracts the ProseMirror snapshot and plain text into pages, rewrites links and queues indexing. Awareness carries presence and cursors. Offline edits merge when the client reconnects.

Versions

A revision is written on publish, on explicit "save version", and automatically every 30 minutes of active editing. The history view diffs snapshots structurally (ProseMirror JSON), not as text, so a moved paragraph shows as moved.

Comments

Inline comments anchor to a Yjs relative position plus the quoted text. If the anchor is lost after heavy editing, the comment falls back to the quote and is marked "text changed". AI suggestions on a comment thread (the "Apply fix" button) are a diff against the current snapshot applied through the editor transaction, never a raw write.

Consistency checks

On publish and on linked-issue change, the pageContext builder pairs each embedded or mentioned issue with the surrounding paragraph and asks the standard model for contradictions with a strict schema (claim, page location, issue field, confidence). Results land in ai_insights as consistency and feed "About this page" and Docs home's "Needs attention".

Exports and imports

Markdown, HTML and PDF export (PDF via headless Chromium in a worker, optional). Confluence storage format and Markdown import map to the schema through packages/editor/convert/; unknown macros become a labelled placeholder block so nothing is silently dropped.

16. Search and the query language

  • Keyword: search_vector on issues and pages with weights (title A, labels and keys B, body D), GIN indexed, plus pg_trgm on titles and issue keys for prefix and typo tolerance in the ⌘K palette. Results are filtered by the actor's project and space access before ranking.
  • Semantic: chunks of pages and issue descriptions embedded via the embedding role, HNSW index in pgvector, queried with cosine distance and merged with keyword results by reciprocal rank fusion. Absent pgvector or an embedding model, the mode is simply not offered and the UI copy says so.
  • Bemmoly Query Language (LQL), a small, familiar query grammar: project = PLT AND status != Done AND assignee = me AND "spec doc" IS EMPTY ORDER BY updated DESC. Parsed in packages/shared (so the web app can validate and autocomplete) and compiled to parameterised SQL in services/search/lql/. Saved filters, swimlane queries, issue tables in docs and automation conditions all use it. The AI writes LQL from plain English and shows it before running.
  • Autocomplete in the palette is a single trigram query across issues, pages and users with a 100 ms budget; results are cached per session for repeated prefixes.

Updating from inside the app

The sidebar badge in the mocks says "Update". Clicking it has to actually update the server, and a container cannot replace its own image. So the installer adds a small updater container that holds the Docker socket and does nothing except a fixed set of actions on request from the app.

  • Availability: the opt-in daily job fetches a signed release manifest with versions, channels (stable, beta), release notes and a list of changesets that take long on large tables. The badge appears only when a newer version in the chosen channel exists.
  • Security of the updater: holding the Docker socket is root-equivalent on the host, so the updater is deliberately dumb. It accepts only update(tag), rollback() and status(), only from the app over the internal Compose network with a token generated by the installer, only for tags from the official registry that pass signature verification. It has no inbound port. Admins who do not want it run the installer with --no-in-app-updates; the button then shows the CLI command instead.
  • Modules and updates: because all modules ship in the image, one update moves the kernel and every enabled module together. Disabled modules' changesets do not run until they are enabled, so a Docs-only install never pays for Work's schema changes.
  • Kubernetes: the button shows the new version, the release notes and the exact helm upgrade command. Patching the Deployment from inside the pod needs a cluster role most operators will not grant; an optional operator can come later.
  • Air-gapped: the Updates page accepts an uploaded release bundle; the updater loads the images from it and runs the same flow.
  • Downgrades: see "Rolling back after an update" below. The short version: within one minor, rollback keeps your data; only an irreversible changeset forces a restore, and the UI says which applies before you confirm.

Backups

Backups are a kernel feature with a schedule the admin chooses, not a cron line in the installer. The same machinery produces the automatic pre-upgrade backup, the scheduled ones and the manual "Back up now".

What a backup contains

  • Database: pg_dump in custom format, compressed, taken in a single consistent snapshot. The app image ships the Postgres 18 client tools so this works against bundled or external databases.
  • Attachments: only the files added since the previous backup in the same chain. Attachments are content-addressed by SHA-256 and written to storage before their database row exists, so dumping the database first and copying files second guarantees every referenced file is present. Monthly runs take a full copy so a chain never grows unbounded.
  • Manifest: app version, changelog tag, enabled modules, sizes and checksums of every part, and the restore instructions.
  • Not included, and said out loud: the install's .env, which holds the secret key that decrypts provider keys, SMTP passwords and SSO secrets stored in the database. A backup without it restores a workspace whose integrations must be re-entered. The installer's final message and the backup settings page both say to keep a copy of /var/bemmoly/.env somewhere safe.

Restore

  • To the same machine: Settings › Storage and backups lists every backup with version, size and verification status. Restore puts the app into maintenance mode (a page served by the updater), restores into a fresh database, swaps, and runs any pending changesets if the backup is from an older version, so a restore can also be a controlled upgrade. The replaced database is kept for the retention window.
  • To a new machine, the disaster-recovery path: run the installer, copy .env and the backup over (or point at the bucket), run bemmoly restore <backup>. This is tested nightly in CI on a fresh VM.
  • Partial restore: a backup can be mounted read-only as a second database for forensic queries or to recover one deleted page or project through the CLI, without replacing the live workspace.
  • Download: any backup can be downloaded from the settings page for an off-site copy by hand.

Backups run as the system.backup job on the worker role, scheduled by pg-boss from the saved settings; the installer's systemd timer is only a safety net that calls bemmoly backup if the app's own scheduler has not run in 36 hours.

Rolling back after an update

The health check after a swap catches a version that will not start. It does not catch a bug people find an hour later. Rollback therefore has to work after the update "succeeded", after users have written data, and it has to be honest about what it keeps.

What is saved before every update

  • A full pg_dump in custom format and a tarball of attachments, with checksums verified and the dump validated with pg_restore --list. Written to /var/bemmoly/backups and flagged pre_upgrade in the backups table; pushed to S3 too when configured.
  • A changelog tag with the version being left (bemmoly db tag 1.2.4).
  • The previous image, kept locally. Pre-upgrade backups and the previous image are retained for seven days by default (a setting), so a rollback is possible for a week without re-downloading anything.

Two modes, chosen by the changelog

What the admin sees

  • Settings › Updates shows "Updated to 1.3.0 two hours ago" with a Roll back to 1.2.4 button. The button's copy names the mode that applies and, for a restore, the discard count and the export link. Nothing runs until confirmed.
  • Code rollback takes about as long as a container restart. Restore rollback takes the restore time, shown as a progress page served by the updater.
  • Both are audited, both work from the CLI (bemmoly rollback, which prints the same mode and discard summary), and both are available for seven days after the update.
  • On Kubernetes the page shows the helm rollback command and the restore job command for the matching backup, since the pod cannot swap itself.
  • If a user-visible bug is found after the retention window, the answer is a patch release forward, not a rollback, and the release notes say which changesets each version contains so the admin can judge.

Release discipline makes the default mode the common one: a release that contains an irreversible changeset is called out in its notes and in the Update dialog before the admin clicks, so "rollback would need a restore" is known going in, not discovered afterwards.

Server

  • Fastify with JSON-schema serialisation for the hot responses (board view, issue, page), which is several times faster than JSON.stringify on untyped objects.
  • Board view is one SQL statement with CTEs and json_agg, returning cards already grouped; no N+1 anywhere, enforced by a query-count assertion in integration tests.
  • Covering and partial indexes for every list endpoint, verified with EXPLAIN in a test that fails on a sequential scan over issues or pages.
  • Prepared statements through postgres.js, pool sized to CPU count × 2, statement timeout 10 s, idle transaction timeout.
  • ETags on reads, Brotli for static assets with immutable cache headers, HTTP/2 via Caddy.
  • AI and import work never touches the request path.

Client

  • Route-level code splitting with TanStack Router; data for a route is prefetched when its link is hovered or focused, so clicks land on warm cache.
  • TanStack Query holds server state with stale-while-revalidate; WebSocket invalidation replaces polling; mutations are optimistic with rollback on error.
  • Backlog and long lists are virtualised with TanStack Virtual; the board virtualises columns past 200 cards.
  • Fonts self-hosted and preloaded; theme tokens are CSS variables so switching themes is a class change, not a re-render.
  • Editor loads only on doc routes; Yjs state is cached in IndexedDB so a reopened page renders before the socket connects.
  • Web Vitals are reported to /metrics (opt-in) so admins see real user performance in Settings › System.

21. Observability

  • Logs: pino JSON; every line has requestId, userId (hashed in logs), route and duration. Redaction list configured once: cookies, authorization, API keys, email bodies, prompt text.
  • Metrics: Prometheus at /metrics: request latency histograms per route, queue depth and job latency per job, AI tokens and cost per role, WebSocket connections, DB pool stats, cache hit rate for insights.
  • Traces: OpenTelemetry auto-instrumentation for Fastify, pg and outbound HTTP, plus the AI SDK's own spans (model, provider, tokens, cached tokens, tool executions) with input and output recording off by default, exported only when OTEL_EXPORTER_OTLP_ENDPOINT is set.
  • In-product: Settings › System shows health checks, version, queue, last backup, AI spend this month, slowest endpoints today. Most admins will never run Grafana; the product has to tell them what is wrong.
  • Errors: typed errors carry a code; unexpected exceptions are logged with the request id that the user sees in the error toast, so a bug report has a handle.

23. Contributing model

Ten-minute start

git clone, pnpm i, pnpm dev. That starts Postgres in Docker, runs the changelog with the demo context so the Acme Labs sample data from the mocks is loaded, starts server and web with hot reload, and opens the app with a logged-in admin. A devcontainer and Codespaces config do the same in the browser.

Extension points

Every pluggable capability has a CONTRIBUTING section with a template: AI provider, email sender, object store, importer, SSO provider, workflow rule, automation action, editor node, theme preset. Each is one file plus one registry line.

Decisions are written

ADRs in docs/adr/, one per decision in this document and every future one. A PR that changes an ADR'd behaviour links the ADR. This document becomes ADR-0001.

Reviews

Conventional commits, one approval, CI green, visual check noted in the PR for UI changes. Maintainers triage weekly; good first issue and help wanted are curated, not auto-labelled.

Releases

Monthly minor, patch as needed. Release PR generated by the changesets release tool; image, Helm chart, air-gap bundle and installer tag published together; release notes list schema changesets and config changes.

Community

GitHub Discussions for questions, Discord for chat, a public roadmap board that is itself a Bemmoly instance (the live demo), security address in SECURITY.md.
