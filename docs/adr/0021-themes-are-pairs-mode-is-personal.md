# ADR 0021: Themes are pairs; mode is personal

- Status: accepted
- Date: 2026-10-11
- Supersedes: the preset parts of [ADR 0005](0005-classic-preset-exact-others-derived.md) and
  [ADR 0015](0015-premium-visual-system.md) (the eight presets, a preset's mode and typeface,
  the single-mode custom builder and brand-tinted surfaces)
- Evidence: the theme review (`docs/design-review/bemmoly-theme-review.html`), approved by the
  owner with every default, plus a custom theme option

## Context

Bemmoly shipped eight presets, each a colour and a mode welded together: six existed in one mode
only, and five accents already meant something else (Forest was Done green, Rose the error red,
Midnight the AI lilac, Warm sat between Incident orange and the warning amber, Ocean on Sub-task
cyan). Every dark preset dropped the Task tile under 3:1. Mode followed the workspace, not the
person, and "system" meant "workspace default", never the operating system.

## Decision

1. **Five themes, each a designed pair.** Bemmoly (default, logo blue), Graphite (true greys,
   ink buttons), Sand (warm neutrals, logo blue), Pine (`#17675A`, hue 170, clear of Done green)
   and High contrast. Each ships a light and a dark set of the same fifteen tokens
   (`THEME_TOKENS`: four surfaces, two lines, three text greys, six accent tokens). A theme with
   one mode cannot be added; a test enforces it.
2. **A theme changes only those fifteen tokens.** The logo, `brand-1/2/3`, AI lilac, statuses,
   signals, type, epic and avatar colours are fixed per mode, never per theme. Dark mode lifts the
   Task tile to `brand-2` and Epic to `#7D68D8` so both pass 3:1. No theme changes the typeface.
3. **Fourteen checks per set.** `themeChecks` (in `@bemmoly/ui/theme`) measures text, links,
   buttons, focus, selection, AI text, the to-do glyph, the Task and Epic tiles, error text and
   control borders; High contrast is held to 7:1 text and 3:1 borders. The token tests run them
   on every theme and mode.
4. **Reserved hues.** No accent may be red (340–12°), amber/orange (18–50°), green (120–155°) or
   lilac/violet (255–290°). A custom colour in a reserved band gets a warning, never a block.
5. **Mode is independent and personal.** `light | dark | system`, where system follows
   `prefers-color-scheme` live (CSS for first paint, `matchMedia` in the app). A person's mode
   and, when the workspace allows it, their theme are stored on their account
   (`user_appearance_preferences`, `PUT /me/appearance`) and cached on the device for first
   paint only. The workspace sets the default theme (`appearance.theme`, with
   `appearance.customThemeId` for a custom one) and the default mode (`appearance.defaultMode`);
   new workspaces default to Match system. Resolution: preview, person, workspace, then Bemmoly
   with Match system.
6. **The typeface is its own setting** (`appearance.font`, `data-font`). Migrated workspaces keep
   the face their preset implied.
7. **Custom themes.** A custom theme is a name, a brand colour and a surface style (neutral from
   Bemmoly, warm from Sand), stored in `custom_themes`; its light and dark sets are generated by
   `buildCustomTheme`, which moves only the accent tokens, the least that passes all fourteen
   checks, and never touches the logo. Admins create workspace themes and may make one the
   default; anyone may create their own while personal themes are on. Brand-tinted surfaces are
   dropped.
8. **Migration** (changeset `0600-appearance-themes`): Classic, Dark, Midnight, Ocean and Rose
   become Bemmoly in their old mode; Slate becomes Graphite, Warm Sand, Forest Pine. The old mode
   becomes the workspace default mode and the old face stays. A stored custom brand becomes a
   workspace custom theme. The retired keys (`appearance.mode`, `surfaces`, `memberModeSwitch`)
   stay readable for the previous minor and are removed later. Saved device choices map the same
   way and are written to the account once.

## Consequences

- `PRESETS`, `themeById`, `buildTheme` and `contrastCheck` are gone; code uses `THEME_SOURCES`,
  `resolveTheme(id, mode)` and `buildCustomTheme`.
- `theme.css` emits `[data-theme][data-mode]` blocks and a `prefers-color-scheme` block for
  `data-mode='system'`; the typeface comes from `[data-font]`.
- Emails use the workspace theme's light set (a custom theme's checked ramp, never the raw hex).
- The demo takes `?theme=pine&mode=dark`; old preset ids still work.

## Amendment (2026-10-11): only a workspace admin sets the theme

The owner narrowed points 5 and 7: **the theme is the workspace's, set only by a workspace admin;
the mode is the only personal appearance choice.**

- Setting the workspace theme (the `appearance.*` settings and workspace custom themes) needs
  `workspace.appearance.manage`, which only Org admin holds by default; anyone else gets 403.
- Personal themes are retired. `PUT /me/appearance` refuses a `theme` with 403 and stores only
  the mode; a theme stored before is ignored (`/me` reports `theme: null`). Creating a
  `personal` custom theme is refused, and personal themes left from before are never listed,
  edited or applied. `appearance.personalThemes` is inert and always reported `false`; it, the
  `theme` column and the `personal` scope stay for the previous minor and are removed later.
- The sidebar's Appearance button (beside the person's name) offers Light, Dark and Match
  system only. Settings › Appearance shows a non-admin the workspace theme read-only with "Your
  workspace admin sets the theme", beside their own mode.
- Resolution once signed in: preview, the person's mode, then the workspace theme and default
  mode. Before sign-in the device cache and the public look still apply.
