Where Work stands, and how we finish it

Shrijayan built the contracts, the server core and the design-system pieces of the Work module on feat/work-module-integration before his credits ran out. The server can already create projects, issues and workflows, and compile LQL to SQL. The screens are not built yet, and boards, sprints, saved filters and metrics have schemas but no services. This page is the inventory and the plan to ship 0.2.0 from his branch.

What stands between the branch and 0.2.0

  • Five screens

    Board with slide-over, Backlog, Issue page with the create form, Board settings, Workflow editor, plus project list and create. The components they need are mostly in packages/ui already.

  • Board, sprint, saved-filter and metrics services

    Schemas and tables exist; the services, routes and tests do not. Sprint close writes the velocity snapshot into sprint_metrics.

  • Labels, versions and components

    Tables and schemas only. The create form and the issue page need them.

  • Tests where it matters most

    Gap-free numbering under concurrent creates, transitions with post-actions, comment threads, links and search have no tests. These need Testcontainers integration tests before release.

  • Kernel touch points

    Register Work search with the command palette, and add a Home extension point for "my work". Both are small kernel changes, reviewed like any other.

  • The integration pass in the plan

    Playwright flows, board p95 against the budget in tech design §20, enable and disable twice, every screen beside its mock.

The plan to finish, in three waves

Each stream is one agent in its own worktree, branched from feat/work-module-integration and merged back into it with green checks. Wave 2 waits only for the server pieces it calls.

Starts now; nothing blocks it.
SERVER · BOARDS

Boards, sprints, filters, metrics

Board configuration (columns, WIP, lanes, card layout, colour rules), sprint create, start and close with the velocity snapshot, backlog endpoints, saved filters shared with a team, velocity, burndown, cycle time and throughput.

SERVER · HARDENING

Labels, versions and components services; integration tests for numbering, transitions, comments, links and search; Work search in the command palette; the kernel Home extension point and the "my work" lists.

WEB · ISSUE

WEB · WORKFLOW

How we work on it

Authorship

Commits to the Work module, its design-system components and its plan are authored as Shrijayan <81805145+shrijayan@users.noreply.github.com>, the address on his own commits, so GitHub links them to his profile. Kernel and release commits stay with Keerthivasan. One author per commit, no co-author lines.

Merging

Streams merge into feat/work-module-integration. The final pull request to main uses Create a merge commit: it keeps every commit and its author exactly. Squash would fold them into one commit, and rebase can fail on the merge commits already in the branch.

Ground rules

The mocks are the pixel source; every screen is checked in a browser beside its mock. AGENTS.md applies: no file over 300 lines, a changeset per schema or user-visible change, green checks before every merge.
